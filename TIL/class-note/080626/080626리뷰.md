## 5강. Python 프로그래밍 — venv·Jupyter·자료구조·함수·객체지향·타입 힌트

### 핵심 개념

ROS2 노드, 인지 알고리즘, 데이터 분석, 시뮬레이션까지 로봇 개발에서 Python은 거의 모든 곳에 등장한다. C++보다 느리지만 작성 속도가 빠르고 생태계가 방대해서, "일단 Python으로 빠르게 만들고 성능이 필요한 부분만 C++로" 가는 것이 로봇 소프트웨어의 일반적인 전략이다. 이 강의는 문법 나열이 아니라 **로봇 코드를 구조적으로 쓰기 위한 Python의 뼈대**(환경 격리, 자료구조 선택, 코드 구조화, 객체지향, 타입 힌트)를 다룬다.

**venv — 프로젝트마다 독립된 패키지 공간**

프로젝트 A는 `numpy 1.26`이 필요한데 프로젝트 B는 옛날 코드라 `numpy 1.19`에서만 돌아가는 상황이 반복된다. 시스템에 numpy는 하나만 설치할 수 있으니 버전 충돌이 나고, 더 위험한 것은 시스템 Python(OS와 ROS2가 쓰는)에 `pip install`을 남발하다가 시스템 도구 자체가 망가지는 경우다. 해결책이 **가상환경(venv)**이다.

```bash
python3 -m venv .venv        # 생성 (프로젝트 디렉터리에서, 1회)
source .venv/bin/activate    # 활성화 — 프롬프트에 (.venv)가 붙는다
pip install numpy matplotlib # 이 방에만 설치됨
pip freeze > requirements.txt # 설치 목록 기록 (팀 공유용)
deactivate                    # 방에서 나오기
```

> "시스템 Python은 성역, 작업은 항상 venv 안에서"

팀원은 `pip install -r requirements.txt` 한 줄로 같은 환경을 재현한다. 필기에 남긴 실무 관점도 같은 맥락이다 — **로봇 환경에서는 노트북 커널이 venv를 자동으로 활성화하도록 맡기지 않는 편이 좋다**는 것. 커널이 어떤 파이썬을 물고 있는지 항상 명시적으로 확인하는 습관이, 뒤에 나올 "분명히 설치했는데 ImportError" 문제를 예방한다.

**Jupyter Notebook — 브라우저·서버·커널의 3층 구조**

우리가 보는 화면은 브라우저일 뿐이고, 코드는 Jupyter 서버를 거쳐 **커널**에서 실행된다. 변수와 import는 전부 커널의 메모리에 있고, 커널이 죽으면 변수도 사라진다. `ipykernel install` 단계를 빠뜨리면 노트북이 시스템 파이썬으로 돌아, 분명히 설치했는데 `ImportError`가 나는 흔한 함정에 빠진다 — 셀에서 `import sys; print(sys.executable)`로 어느 파이썬이 도는지 항상 확인할 수 있다.

> 셀은 각각 독립된 프로그램이 아니라 **같은 커널 메모리를 이어서 건드리는 조각**이다.

위아래로 오가며 실행하면 화면의 코드 순서와 실제 실행 이력이 어긋난다. 셀 왼쪽 실행 카운터 `[n]`이 위에서 아래로 증가하는지가 판별 기준이며, 제출·공유 전에는 `Kernel → Restart Kernel and Run All Cells`로 확인하는 습관이 "내 화면에서는 되던데요"를 막는다. 자주 쓰는 단축키는 다섯 개면 충분하다.

| 단축키 | 동작 |
|---|---|
| `Shift + Enter` | 셀 실행 후 다음 셀로 이동 |
| `Ctrl + Enter` | 셀 실행 후 그 자리에 머무름 |
| `Esc → A / B` | 위 / 아래에 새 셀 삽입 |
| `Esc → M / Y` | 마크다운 셀 / 코드 셀로 전환 |
| `Esc → D D` | 셀 삭제 |

노트북은 탐색과 설명에 강하고 재사용할 코드를 담기엔 약하다 — **두 번 쓰는 코드는 `.py` 모듈로 옮기는 것**이 원칙이다.

**자료구조 — list, tuple, dict, set을 언제 쓰나**

Python의 4대 내장 자료구조는 각각 다른 문제를 푼다. 순서 있는 목록이면 **list**, 바뀌면 안 되는 값 묶음이면 **tuple**, 이름으로 찾는 표라면 **dict**, 중복 없는 모음·소속 검사라면 **set**이다.

```python
distance_log = []                # list — 순서 있는 시계열, 추가/삭제가 잦다
home_position = (0.0, 0.0, 0.0)  # tuple — 불변. home_position[0]=1.0 → TypeError!
sensor_values = {"lidar": 0.83, "battery": 11.9}  # dict — 키로 즉시 조회, O(1)
detected_ids = {3, 7, 12}
if 7 in detected_ids:            # set — O(1). list의 in은 O(n)
    print("장애물 7 추적 중")
```

| 연산 | list | dict / set |
|---|---|---|
| 끝에 추가 | O(1) | O(1) |
| 인덱스 접근 `a[i]` | O(1) | — |
| 포함 검사 `x in a` | O(n) — 전부 뒤짐 | O(1) — 해시로 즉시 |
| 중간 삽입/삭제 | O(n) | O(1) |

dict/set은 내부적으로 해시 테이블을 써서 키를 해시 함수에 넣어 "몇 번째 서랍에 있는지"를 바로 계산하므로 크기와 무관하게 빠르다. 원소 100개일 때는 체감이 안 되지만 100만 개가 되면 약 **2,500배** 차이가 난다. 30Hz로 도는 인지 루프 안에서 `in` 검사를 list로 하면 처음엔 잘 돌다가 데이터가 쌓일수록 마감을 놓치는 성능 버그가 된다 — 노트북에서 `%timeit x in my_list`로 직접 재볼 수 있다.

정렬 알고리즘의 시간복잡도도 같은 맥락이다. 버블 정렬은 평균·최악 `O(n²)`이지만, 이미 거의 정렬된 데이터라면 조기 종료 덕분에 최선의 경우 `O(n)`까지 빨라진다 — "정렬 알고리즘도 최선/평균/최악 케이스에 따라 비용이 크게 달라진다"가 핵심이지, 버블 정렬 자체가 일반적으로 빠른 알고리즘이라는 뜻은 아니다.

**함수와 객체지향 — 이벤트에 반응하는 코드 단위**

함수에서 가장 흔한 함정은 **가변 기본 인자**다.

```python
def add(v, log=[]):
    log.append(v)
    return log

print(add(1))  # [1]
print(add(2))  # [1, 2]  — 새 리스트가 아니라 같은 리스트를 계속 공유한다
```

기본값 `[]`는 함수 **정의 시점**에 단 한 번만 만들어져 이후 모든 호출이 이를 공유한다. 매 호출마다 새 리스트가 생긴다고 착각하기 쉬운 대표적인 함정이다.

객체지향을 쓰는 이유는 이벤트가 발생할 때마다 객체를 참조해 코드를 해석·실행하기 위해서다 — 상태와 행동을 객체 하나에 묶어두면, 호출하는 쪽은 내부 구현을 몰라도 항상 같은 방식으로 다룰 수 있다. 이를 가능하게 하는 두 축이 다음과 같다.

- **오버라이드와 다형성**: 부모 클래스 `Sensor`가 정의한 `read()`를 자식 클래스 `Lidar`, `Imu`가 각자의 방식으로 다시 정의하는 것이 **오버라이드**다. 그 덕분에 호출하는 쪽은 센서 종류를 몰라도 `s.read()`로 동일하게 부를 수 있는데, 이것이 **다형성**이다.
- **매직 메서드**: 내부적으로 자동 호출되는 함수 — 클래스에 `__init__`, `__repr__`, `__add__` 같은 이름을 정의해두면 파이썬이 생성·출력·연산 같은 특정 상황에서 알아서 불러준다.
- **캡슐화**: 클래스 안에서 외부에 공개할 속성·메서드와 감출 속성·메서드를 구분하는 것. 내부 구현이 바뀌어도 바깥에서 쓰는 방식은 그대로 유지된다.

## 6강. NumPy 벡터 연산 — ndarray·슬라이싱·브로드캐스팅

### 핵심 개념

LiDAR 한 바퀴 스캔은 수천 개의 거리값, 카메라 한 프레임은 수백만 개의 픽셀이다. 30Hz 카메라라면 33ms 안에 수백만 픽셀 연산을 끝내야 하는데, 순수 Python 반복문으로는 어림도 없다. 여기서 등장하는 것이 **NumPy**이며 핵심 사상은 하나다 — **"반복문을 쓰지 말고, 배열 전체를 한 번에 연산하라(벡터화)."**

**ndarray가 빠른 이유 — 메모리 구조**

Python list는 포인터들의 목록이라 각 원소가 메모리 여기저기 흩어진 별도 객체다. 반복문이 원소마다 "포인터 따라가기 + 타입 확인 + 객체 연산"을 반복한다. 반면 ndarray는 같은 dtype의 값이 연속된 메모리 한 덩어리라 CPU 캐시에 통째로 올라가고, C로 구현된 내부 루프가 SIMD 명령으로 여러 값을 한꺼번에 처리한다.

> 100만 원소 곱셈 실측: Python for문 412ms, 컴프리헨션 268ms, NumPy 벡터화 7.3ms — 약 **56배** 차이. **ndarray를 만들어 놓고 Python for문으로 원소를 하나씩 돌면 NumPy의 이점이 전부 사라진다.**

**shape·dtype·axis — 다차원 배열 다루기**

| 데이터 | shape | 의미 |
|---|---|---|
| LiDAR 1스캔 | `(360,)` | 각도별 거리 |
| 위치 궤적 | `(N, 3)` | N개 시점 × (x, y, z) |
| 회전 행렬 | `(3, 3)` | 3차원 회전 |
| 컬러 이미지 | `(H, W, 3)` | 높이 × 너비 × RGB |

`axis=k`는 **"k번째 차원을 붕괴시킨다"**로 외우면 헷갈리지 않는다. shape `(3, 3)`인 궤적 배열에서 `axis=0`으로 평균을 내면 시점 방향이 붕괴되어 좌표별 평균 `(3,)`이 남고, `axis=1`이면 좌표 방향이 붕괴되어 시점별 평균이 남는다. 결과의 shape을 먼저 떠올리는 습관이 다차원 배열 사고의 핵심이다.

dtype도 실무에서 중요하다. `uint8`(0~255)끼리 더하면 255를 넘는 순간 0으로 되감겨 `250 + 10`이 `4`가 되는 오버플로 함정이 있다 — 계산 전 `img.astype(np.float64)`로 승격하는 것이 관례다.

| dtype | 표현 범위 | 크기 | 쓰임 |
|---|---|---|---|
| `uint8` | 0~255 | 1B | 이미지 픽셀 |
| `float32` | 약 ±3.4e38 | 4B | GPU·딥러닝 텐서 |
| `float64` | 약 ±1.8e308 | 8B | 좌표·회전 계산(NumPy 기본) |

> shape만큼이나 dtype을 의심하라 — 값이 이상하면 절반은 dtype 문제다.

**슬라이싱은 뷰, 마스킹·팬시 인덱싱은 복사**

```python
roi = img[100:200, 300:400]
roi[:] = 0        # img의 해당 영역도 검게 변한다! 같은 메모리를 보고 있기 때문
safe = img[100:200, 300:400].copy()  # 독립 사본이 필요하면 .copy()
```

슬라이스로 잘라낸 영역은 원본과 **같은 메모리를 가리키는 뷰(view)**다. 5강의 `b = a` 참조 문제와 같은 계열의 함정이라, 노트북에서 셀을 다시 실행할 때마다 원본이 오염될 수 있으니 의심스러우면 `.copy()`가 안전하다.

불리언 마스킹은 벡터화의 꽃이다 — **조건식 → True/False 마스크 → 그 마스크로 선택**이라는 세 박자.

```python
scan = np.array([0.3, 8.2, 0.5, 12.0, 0.45, 9.9])
near = scan[scan < 1.0]                        # [0.3, 0.5, 0.45] — 1m 이내 장애물만
valid = scan[(scan > 0.1) & (scan < 10.0)]     # 복합 조건: & (and), | (or), 괄호 필수!
```

반복문+조건분기로 5줄 넘게 걸릴 코드가 한 줄이 되고 속도도 수십 배 빨라진다.

**브로드캐스팅 — 모양이 달라도 메모리 복사 없이 연산**

규칙은 두 가지, shape을 **뒤에서부터** 짝지어 비교한다.

1. 두 크기가 같거나,
2. 한쪽이 1이면 → 호환(1인 쪽이 상대 크기로 늘어남)

`(480, 640, 3)` 이미지에 `(3,)` 채널별 계수를 곱하면 각 행에 자동으로 "늘려져" 적용되며, 실제 메모리 복사는 일어나지 않는다. 로봇 코드에서 특히 중요한 패턴이 좌표 변환이다.

```python
traj_centered = traj - traj[0]   # 궤적 전체를 원점 이동: (N,3) - (3,)
traj_rot = traj @ R.T            # (N,3) — N개의 점을 한 번에 회전! 반복문 없음
```

이 패턴은 모듈 ②의 TF2 좌표 변환, 로봇 기구학이 전부 "점들의 배열 × 회전 행렬"이며 NumPy에서는 `@` 하나로 끝난다는 점과 직결된다.

**벡터화 사고방식 — 반복문을 지우는 연습**

| 반복문 패턴 | 벡터화 대응 |
|---|---|
| 원소마다 계산 | 배열 전체 연산(`a*2`, `np.sin(a)`) |
| if로 걸러서 모으기 | 불리언 마스킹(`a[cond]`) |
| if로 값 바꾸기 | `np.where(cond, x, y)` 또는 `a[cond] = x` |
| 합·평균·최대 구하기 | `sum()`, `mean()`, `max()` (+axis) |
| 두 배열 짝지어 계산 | 같은 shape 연산 또는 브로드캐스팅 |
| 최솟값의 위치 찾기 | `np.argmin`, `np.argmax` |

이 표만 체득해도 인지·제어 데이터 처리 코드의 90%를 벡터화할 수 있고, 이 감각은 모듈 ④의 제어 시뮬레이션과 이후 PyTorch(문법이 NumPy와 거의 동일)로 그대로 이어진다.

7. shape이 `(4, 3)`인 배열 `data`에 대해 `data.mean(axis=0)`과 `data.mean(axis=1)`의 결과 shape을 각각 쓰고, 각각 무엇의 평균인지 설명하시오. - (4,) (,3) axis=0 은 행을 남기고 axis=1 은 열만 남기고 계산한다.
**채점: X**
> [!question]- 정답 및 해설
> 정답: `axis=0` → shape `(3,)`, 행(0번째 차원)이 붕괴되어 **열별 평균**(각 컬럼을 세로로 평균)이 남는다. `axis=1` → shape `(4,)`, 열이 붕괴되어 **행별 평균**이 남는다.
> shape을 axis=0/1 순서대로 `(4,) (,3)`으로 적어 서로 뒤바뀌었고(`(,3)`도 `(3,)`의 오타로 보임), "axis=0은 행을 남기고"라는 설명도 반대다. `axis=k`는 "k번째 차원을 붕괴시킨다"로 외우는 것이 안전하다.

9. shape이 `(100, 3)`인 좌표 배열과 shape이 `(3,)`인 벡터를 곱셈할 수 있는 이유를 브로드캐스팅 규칙으로 설명하시오. - 행렬 곱의 법칙으로 앞뒤의 행렬이 열과 행이 같다면 곱셈이 가능 하고 행렬이 압축 된다.
**채점: X**
> [!question]- 정답 및 해설
> 정답: `*` 연산은 행렬곱이 아니라 원소별(element-wise) 곱셈이다. 브로드캐스팅은 shape을 **뒤에서부터** 짝지어, 크기가 같거나 한쪽이 1이면 호환되는 규칙이다. `(100,3)`과 `(3,)`은 마지막 차원이 둘 다 3이라 호환되고, `(3,)` 쪽이 100번 "늘어난 것처럼" 각 행에 적용된다(실제 메모리 복사는 없음).
> "행렬 곱의 법칙(행·열 일치)"은 `@` 연산(내적)의 규칙이지 브로드캐스팅 규칙이 아니다 — 서로 다른 개념이 섞였다.
