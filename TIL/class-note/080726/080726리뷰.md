## 6강 실습. NumPy 벡터 연산 — LiDAR 좌표 변환

### 핵심 개념

**왜 극좌표 → 직교좌표 변환이 필요한가**

LiDAR는 레이저를 쏘는 부분과 반사값을 받는 부분이 한 몸으로 붙어 360도 회전하면서 측정하는 센서다. 그래서 원본 데이터는 "몇 도 방향에서 얼마나 떨어져 있는지"라는 **극좌표(각도, 거리)** 형태로 나온다. 반면 경로 계획이나 지도 작성은 로봇 중심의 x·y 평면(직교좌표) 위에서 이뤄지므로, 인지 파이프라인의 첫 관문은 항상 이 극좌표를 직교좌표로 바꾸는 작업이다. 오늘 실습은 이 변환을 실제 배열 360개(각도별 거리)를 놓고 끝까지 처리해보는 흐름이었다.

**1단계 — 불리언 마스크로 유효 측정 걸러내기**

센서 사양(0.1m 초과 ~ 10m 미만)을 벗어난 값은 노이즈로 버려야 한다.

```python
mask = (scan > 0.1) & (scan < 10.0)
valid = scan[mask]
```

여기서 조건을 `and`가 아니라 `&`로, 그리고 각 조건을 반드시 괄호로 감싸는 이유는 numpy 배열의 비교·논리 연산은 원소 단위(element-wise)로 일어나고, `&`·`|`의 연산자 우선순위가 비교 연산자보다 높기 때문이다. 괄호 없이 쓰면 `scan > (0.1 & scan) < 10.0`처럼 엉뚱하게 묶여 에러가 나거나 의도와 다른 결과가 나온다.

**2단계 — 인덱스 정합성: mask를 "같이" 적용해야 한다**

`valid = scan[mask]`로 걸러낸 순간 `valid`는 원래 360개짜리 배열보다 짧아진다. 이 상태에서 `np.argmin(valid)`로 얻은 인덱스는 **valid 안에서의 위치**일 뿐, 원본 `angles` 배열의 인덱스가 아니다. 최근접 장애물의 실제 각도를 구하려면 `angles`에도 **똑같은 mask**를 먼저 적용한 뒤(`angles[mask]`) 같은 인덱스를 써야 한다 — 서로 다른 두 배열을 같은 마스크로 "같이 잘라내야" 대응 관계가 유지된다는 점이 이 문항의 핵심 함정이었다.

**3단계 — 벡터화된 좌표 변환 (반복문 금지)**

```python
x = valid * np.cos(ang_valid)
y = valid * np.sin(ang_valid)
xy = np.column_stack((x, y))   # (N, 2)
```

`r·cosθ`, `r·sinθ`를 배열 전체에 대해 한 번에 계산하고 `column_stack`으로 묶으면 N개의 점을 for문 없이 (N, 2) 배열로 만들 수 있다. 변환은 각 점의 원점까지 거리(=r)를 바꾸지 않으므로, `np.linalg.norm(xy, axis=1)`이 원래 `valid`와 일치하는지가 구현이 맞았는지 확인하는 자체 검증 수단이 된다.

**4단계 — 전방 위험 구간 판정 (각도 wrap-around)**

로봇 전방 ±30°는 각도가 0~2π로 표현될 때 `θ < π/6` **하나만으로는** 표현되지 않는다. 각도 0 근처(막 0을 넘긴 값)와 2π 근처(막 2π에 못 미친 값) 두 구간이 실제로는 같은 "전방"이기 때문에, `(θ < π/6) | (θ > 2π - π/6)`처럼 **OR로 두 구간을 이어야** 정확하다. 여기에 거리 조건을 `&`로 더해 위험 마스크를 만들고, `.any()`로 정지 여부를 파이썬 bool 하나로 축약하는 흐름은 실제 충돌 회피 로직의 축소판이다.

**5단계 — 회전은 길이를 보존한다**

```python
R = np.array([[np.cos(th), -np.sin(th)],
              [np.sin(th),  np.cos(th)]])
xy_rot = xy @ R.T
```

점들이 **행(row)**으로 쌓여 있는 `(N, 2)` 배열이므로, 각 행 벡터에 회전행렬을 곱하려면 `xy @ R.T` 순서가 맞다. `R @ xy`는 shape가 아예 맞지 않아 계산이 안 되고, `xy @ R`(전치 없이)은 shape은 맞아도 실제로는 다른 변환이 되어 값이 틀어진다. 회전 전후로 각 점의 원점까지 거리가 그대로 보존되는지 확인하는 것이 구현 검증의 핵심이었다.

**6단계 — 벡터화가 빠른 이유**

같은 필터링을 for문(`loop_filter`)과 벡터화(`scan[mask]`) 두 방식으로 짜고 `%timeit`으로 재보면, 오늘 측정에서 for문은 약 25μs, 벡터화는 약 2.3μs로 **10배 이상** 차이가 났다. numpy 벡터화는 반복 처리를 C로 구현된 내부 루프에 통째로 넘기고 파이썬 인터프리터의 오버헤드(매 원소마다 타입 체크·바이트코드 해석)를 건너뛰기 때문이다. 데이터가 100배 커지면 for문은 원소 수에 비례해 시간이 늘지만 벡터화는 상대적으로 오버헤드 비중이 줄어들어, 절대 격차는 더 벌어지는 방향으로 간다 — 5강에서 다룬 list vs set의 O(n) vs O(1) 이야기와 같은 맥락으로, "루프 안에서 반복되는 연산은 자료구조·연산 방식 선택이 성능을 좌우한다"는 원칙이 여기서도 그대로 적용된다.

> 반복 처리가 필요한 순간, 먼저 "이걸 벡터화할 수 있는가"를 묻는 것이 numpy를 쓰는 습관의 핵심이다.

## 부록. SSH 키 생성 — GitHub 인증

### 핵심 개념

GitHub에 코드를 올리거나 받을 때마다 비밀번호(또는 매번 발급하는 토큰)를 입력하지 않으려면 **SSH 키 쌍**으로 인증하는 방식을 쓴다.

```bash
ssh-keygen -t rsa      # 키 쌍(개인키+공개키) 생성
cat 키_경로.pub         # 공개키 내용 확인 — 이 값을 GitHub에 등록
```

`ssh-keygen`은 개인키(로컬에만 보관, 절대 공유 금지)와 공개키(`.pub`, GitHub 계정에 등록) 한 쌍을 만든다. 이후 git이 이 로컬 저장소를 GitHub과 통신할 때 개인키로 서명하고 GitHub은 등록된 공개키로 그 서명을 검증하므로, 매 push/pull마다 자격 증명을 입력할 필요 없이 안전하게 인증된다.

## 복습 문제 10선

**총점: 3.5 / 10** (O=2, △=3, X=5)

1. numpy 배열에서 복합 불리언 조건을 만들 때 `and`/`or` 대신 `&`/`|`를 쓰고 각 조건을 괄호로 감싸야 하는 이유를 설명하라.
   - 답: 연산자 우선순의 법칙으로 순서를 보존 하려면 ()로 우선 연산을 강제해야 한다.
   - 채점: △ — 괄호가 필요한 이유(연산자 우선순위)는 맞혔지만, `and`/`or` 대신 `&`/`|`를 써야 하는 더 근본적인 이유가 빠졌다.
   > [!question]- 정답 및 해설
   > ① `&`/`|`는 원소 단위(element-wise)로 동작하지만 `and`/`or`는 배열 전체를 하나의 참/거짓 값으로 취급하려 해서 "truth value of an array is ambiguous" 에러가 난다. ② `&`/`|`의 연산자 우선순위가 비교 연산자(`>`, `<`)보다 높아서, 괄호 없이 쓰면 `scan > (0.1 & scan) < 10.0`처럼 엉뚱하게 묶여버린다. 두 이유가 함께 괄호를 강제한다.

2. `valid = scan[mask]`로 걸러낸 배열에서 `np.argmin(valid)`로 얻은 인덱스를 원본 360개짜리 `angles` 배열에 그대로 적용하면 왜 안 되는가? 올바르게 대응 각도를 구하는 방법은?
   - 답: valid는 마스킹으로 유효한 원소들이 걸러 졌기 때문에 angles와 는 다른 구조를 가지고 있다 그러므로 angles도 mask 로 유효한 원소를 동일하게 걸러 주는 것이 데이터를 매치시키는데 중요하다.
   - 채점: O — `valid`가 원본보다 짧아져 인덱스가 어긋난다는 점과, `angles`에도 동일한 `mask`를 적용해야 대응 관계가 유지된다는 핵심을 모두 짚었다.
   > [!question]- 정답 및 해설
   > `angles[mask]`로 동일한 마스크를 적용한 뒤, `np.argmin(valid)`로 얻은 인덱스를 `angles[mask]`에 그대로 사용한다.

3. 극좌표 (r, θ)를 직교좌표로 바꾸는 공식을 쓰고, N개의 점을 (N, 2) 배열로 만들 때 for문 대신 벡터화를 써야 하는 이유를 설명하라.
   - 답: x = np.cos(theta) * r, y = np.sin(theta) * r
   - 채점: △ — 변환 공식은 맞았지만, 벡터화를 써야 하는 이유에 대한 설명이 빠졌다.
   > [!question]- 정답 및 해설
   > `x = r·cosθ`, `y = r·sinθ`이 맞다. for문 대신 벡터화를 쓰는 이유는, numpy 벡터화가 반복 처리를 C로 구현된 내부 루프에 넘겨 파이썬 인터프리터의 매 원소별 오버헤드(타입 체크·바이트코드 해석)를 건너뛰기 때문에 훨씬 빠르고, `column_stack`으로 (N, 2) 배열을 한 번에 만들 수 있어 코드도 간결해진다.

4. 로봇 전방 ±30° 범위를 각도 배열(0~2π)에서 마스크로 표현할 때, 왜 `θ < π/6` 조건 하나만으로는 부족한가?
   - 답: 그식은 +30 공간 뿐이다
   - 채점: X — "+30 공간뿐이다"라는 답으로는 왜 부족한지 설명이 되지 않는다. 핵심은 각도가 0~2π로 표현될 때 "전방"이 두 구간으로 쪼개진다는 점이다.
   > [!question]- 정답 및 해설
   > 전방 ±30°는 각도 0 근처(0을 막 넘긴 값)와 2π 근처(2π에 못 미친 값) 두 구간으로 나뉘어 표현되는데, `θ < π/6`은 이 중 앞쪽 구간만 잡아낸다. 뒤쪽(2π 근처) 구간을 놓치므로 `(θ < π/6) | (θ > 2π - π/6)`처럼 OR로 두 구간을 이어야 한다.

5. `xy_rot = xy @ R.T`에서 전치(`.T`)를 빼고 `xy @ R`을 쓰면 어떤 문제가 생기는가? (점들이 행으로 쌓여 있다는 조건에서 답하라)
   - 답: (미작성)
   - 채점: X (미답) — 답이 작성되지 않았다.
   > [!question]- 정답 및 해설
   > 점들이 `(N, 2)` 형태로 행(row)으로 쌓여 있을 때, 각 행 벡터에 회전행렬을 곱하려면 `xy @ R.T` 순서가 맞다. `xy @ R`은 shape은 맞아 계산은 되지만, 실제로는 의도한 회전과 다른 변환이 되어 좌표 값이 틀어진다(회전 후에도 원점까지 거리가 보존되는지로 검증 가능).

6. 회전 변환 구현이 올바른지 검증할 때 "회전 전후로 원점까지의 거리가 보존된다"는 성질을 어떻게 활용할 수 있는가?
   - 답: (미작성)

7. for문 버전과 벡터화 버전의 실행 시간을 비교했을 때 벡터화가 훨씬 빠른 이유는 무엇이며, 데이터 크기가 100배 커지면 두 방식의 시간 격차는 어떻게 변하는가?
   - 답: 벡터화는 for문 필요 없이 원소를 계산한다. 100배 커지면 기하 급수적으로 커짐
   - 채점: △ — 벡터화가 빠른 이유의 방향은 맞지만 근거가 얕고("for문 필요 없이"), 데이터가 100배 커질 때 격차가 "기하급수적으로" 커진다는 서술은 틀렸다 — 실제로는 절대 격차가 벌어지는 것이지 지수적 증가가 아니다.
   > [!question]- 정답 및 해설
   > 벡터화가 빠른 이유는 반복 처리를 C로 구현된 내부 루프에 통째로 넘겨 파이썬 인터프리터의 매 원소별 오버헤드(타입 체크·바이트코드 해석)를 건너뛰기 때문이다. 데이터가 100배 커지면 for문은 원소 수에 비례해 시간이 늘지만, 벡터화는 상대적으로 오버헤드 비중이 줄어들어 절대 시간 격차는 더 벌어지는 방향으로 간다(지수적 증가는 아님).

8. 30Hz로 도는 인지 루프에서 누적된 ID 목록에 소속 검사를 반복해야 한다면 list 대신 set을 쓰는 것이 원칙인 이유를 O(n)/O(1) 관점에서 설명하라.
   - 답: set은 인덱싱 대신 id 로 해당 원소의 중복을 찾는데 아주 빠르다. 리스트가 늘어나도 찾는 원소가 a 개 라면 동일한 시간 복잡도를 가진다. 반면 list는 인덱싱으로 직접 비교하며 중복을 가려내야 하기 때문에 데이터가 많아지면 많은만큼 시간 복잡도가 올라간다.
   - 채점: O — set은 해시 기반으로 데이터 크기와 무관하게 O(1), list는 순회가 필요해 O(n)이라는 핵심 대비를 잘 짚었다. (표현을 다듬으면: "id로 찾는다"보다는 "해시로 위치를 계산한다"가 더 정확하다.)
   > [!question]- 정답 및 해설
   > list의 포함 검사(`in`)는 전체를 순회해야 해 O(n), set/dict는 해시 테이블 구조상 즉시 위치를 계산해 O(1)이다. 30Hz 루프에서 ID 수가 누적될수록 list는 검사 시간이 선형으로 늘어 마감을 놓치는 성능 버그로 이어지지만, set은 데이터가 많아져도 검사 시간이 거의 일정하다.

9. `ssh-keygen -t rsa`로 생성한 키 쌍 중 GitHub 계정에 등록해야 하는 것은 개인키와 공개키 중 무엇이며, 이 방식으로 인증하면 어떤 점이 편해지는가?
   - 답: 개인키, 인증된 기기에서 다른 인증 없이 올리거나 받을 수 있다.
   - 채점: X — 등록 대상이 반대로 되어 있다. GitHub에 등록하는 것은 **공개키**(`.pub`)이고, 개인키는 로컬에만 보관하며 절대 공유하면 안 된다. 편해지는 점에 대한 설명은 방향이 맞다.
   > [!question]- 정답 및 해설
   > 공개키(`.pub`)를 GitHub 계정에 등록한다. 이후 git이 로컬 저장소에서 GitHub과 통신할 때 개인키로 서명하고 GitHub은 등록된 공개키로 그 서명을 검증하므로, 매 push/pull마다 비밀번호나 토큰을 입력하지 않고도 안전하게 인증된다.
