## 4강. Git과 협업 워크플로우

### 핵심 개념

로봇 프로젝트의 흔한 사고: 팀원 A가 LiDAR 드라이버를, 팀원 B가 같은 파일의 모터 제어 코드를 동시에 고치면 B의 저장이 A의 하루치 작업을 덮어쓴다. **버전 관리 시스템(VCS)**, 그중 사실상 표준인 **Git**이 이 문제를 해결한다.

- **스냅샷(snapshot)**: Git은 "무엇이 바뀌었나(차이)"가 아니라 **그 시점 프로젝트 전체의 모습**을 저장한다. 각 스냅샷이 **커밋(commit)**이며 고유 해시 ID(예: `a3f9c2e`)를 갖고, 부모를 가리키는 사슬로 연결되어 **이력(history)**이 된다. 즉 Git 이해의 본질은 "커밋 노드의 그래프와 그것을 가리키는 포인터"다.
- **분산(distributed)**: 모든 개발자의 PC에 **저장소 전체 이력의 완전한 복사본**이 있다. GitHub는 "중앙"이 아니라 팀이 합의한 만남의 장소일 뿐이며, 네트워크가 필요한 건 `push`·`pull`·`clone` 세 가지뿐이다.
  > SVN 같은 중앙집중형은 서버에 못 붙으면 커밋조차 못 한다. **클라우드(원격 서버)에만 의존해 작업하면 서버가 죽는 순간 복구할 길이 없다** — 로컬에 이력 전체를 갖고 있는 Git의 분산 구조가 로봇 현장(공장·야외의 불안정한 네트워크)에서 특히 고마운 이유다.

**Git의 4개 공간**과 데이터 이동 순서:

| 공간 | 역할 | 이동 명령 |
|---|---|---|
| 작업 디렉터리 (Working Dir) | 실제 파일 편집 | — |
| 스테이징 영역 (Staging) | 커밋할 변경만 선별 | `git add` |
| 로컬 저장소 (.git) | 커밋 이력 보관 | `git commit` |
| 원격 저장소 (GitHub) | 팀과 공유 | `git push` / `git pull` |

스테이징이 중간에 있는 이유는 **"수정한 것 중 일부만 골라 의미 있는 단위로 커밋"**하기 위해서다. 매일 반복하는 흐름은 `git status`(무엇이 바뀌었는지, 뭘 하기 전에도 먼저)→`git diff`(줄 단위 확인)→`git add`→`git commit -m`→`git push`. `git log --oneline --graph`로 이력을 그래프로 보는 습관도 같은 맥락이다.

> **커밋 메시지는 미래의 팀원(그리고 미래의 나)에게 보내는 기록**이다. "수정", "fix" 같은 메시지는 6개월 뒤 아무 정보가 없다 — "무엇을, 왜"가 담기게 쓴다. 한 커밋 = 한 가지 일로 자르면 문제가 생겨도 그 부분만 되돌릴 수 있다.

실무에서 흔히 쓰는 커밋 메시지 접두어(conventional commits):

| 접두어       | 의미                      |
| --------- | ----------------------- |
| `Feat:`   | 새 기능 추가                 |
| `Fix:`    | 버그 수정                   |
| `Test:`   | 테스트 추가/수정               |
| `Design:` | 설계 변경                   |
| `Style:`  | 코드 스타일(포맷팅 등, 로직 변경 없음) |
| `Docs:`   | 문서 수정                   |

**브랜치(branch)**는 특정 커밋을 가리키는 41바이트짜리 포인터일 뿐이라 만드는 데 비용이 거의 없다. `git switch -c feature/lidar-driver`로 생성·이동, `git switch main`으로 언제든 복귀해도 작업물은 브랜치에 그대로 남는다.

> **main은 항상 동작하는 코드만 둔다.** 직접 커밋하지 않고 병합으로만 갱신한다. 실험적인 제어 게인 튜닝, 새 센서 드라이버는 전부 `feature/...` 브랜치에서 진행한다. 브랜치는 **작게·짧게**(하루~며칠) 유지한다 — 두 주 동안 혼자 굴린 브랜치는 병합 시점에 수십 개의 충돌을 낸다.

**merge vs rebase** — 결과 코드는 같아도 이력의 모양이 달라진다.

| 구분 | merge | rebase |
|---|---|---|
| 동작 | 두 갈래를 합치는 **병합 커밋 M**을 새로 만든다 | 내 커밋들을 최신 main 끝으로 옮겨 다시 쌓는다(C1→C1′) |
| 이력 | 갈라졌다 합쳐진 모양 그대로 보존 | 한 줄로 깔끔하게 정리(단, 커밋을 새로 씀) |
| 용도 | 공유 브랜치(main)에 기능 합치기 — PR 병합 | 내 로컬 브랜치를 최신 main과 동기화 |

> **판단 기준은 하나: 다른 사람이 이 커밋을 봤을 수 있는가.** 원격에 push해서 다른 사람이 봤을 수 있는 커밋은 절대 rebase하지 않는다 — rebase는 커밋을 "새로 다시 쓰는" 것이라, 공유된 이력을 rebase하면 팀원의 로컬에는 옛 커밋이, 원격에는 새 커밋이 남아 이력이 갈라지고 강제 push로 남의 커밋이 사라지거나 pull마다 유령 충돌이 난다. **아직 나만 가진 로컬 커밋**에서만 rebase를 마음껏 쓴다.

**충돌(conflict)**은 같은 파일의 같은 부분을 양쪽에서 다르게 고쳤을 때만 나며(다른 파일·다른 줄은 Git이 알아서 합침), 오류가 아니라 "여기는 사람이 정해 주세요"라는 정상적인 질문이다.

```
def get_max_speed():
<<<<<<< HEAD
    return 0.8  # 안전을 위해 감속 (main의 변경)
=======
    return 1.2  # 성능 테스트용 증속 (내 브랜치의 변경)
>>>>>>> feature/speed-tuning
```

해결은 세 단계: ① `<<<<<<<`/`=======`/`>>>>>>>` 표식을 모두 지우고 두 버전을 읽어 **올바른 최종 코드를 직접 작성**(둘 중 하나가 아니라 제3의 코드일 수 있다 — 예: "안전 한도 0.8 유지 + 테스트 플래그로 1.2 허용") ② `git add 파일명`으로 해결 표시 ③ `git commit`(merge 중) 또는 `git rebase --continue`(rebase 중)로 마무리. 해결 뒤엔 반드시 빌드·테스트로 확인한다 — 표식만 지워 컴파일은 되는데 로직이 깨진 상태가 가장 위험하다. 예방책은 브랜치를 짧게 유지하고 `git pull` 후 rebase로 main과의 격차를 자주 줄이는 것.

**Pull Request(PR)**는 브랜치가 main에 들어가는 관문 — "내 브랜치를 main에 당겨가(pull) 주세요"라는 요청+리뷰의 장이다.

> ① 브랜치 생성 → ② 작업·커밋 → ③ 푸시 → ④ PR 생성 → ⑤ 코드 리뷰(수정 요청 시 ②로 복귀) → ⑥ CI 테스트 통과 → ⑦ main 병합·브랜치 삭제

리뷰가 형식 절차가 아닌 이유는 **결함 조기 발견**(로봇 코드 버그는 물리적 사고가 된다), **지식 공유**("그 부분은 A만 안다" 위험 감소), **컨벤션 유지**, **기록**(왜 이 설계를 골랐는지가 커밋 메시지가 못 담는 맥락으로 PR 스레드에 남음) 때문이다. 리뷰어는 사람이 아니라 **코드의 문제**를 지적하고, 작성자는 방어 대신 **의도를 설명**한다. PR은 리뷰 가능한 크기(수백 줄 이내)로 작게 유지한다 — 1000줄짜리 PR은 아무도 제대로 못 읽고 "LGTM"만 달린다.

**심화 — CI(지속적 통합)**: push·PR마다 서버가 자동으로 빌드·테스트를 돌리는 체계. `colcon build`가 깨지지 않는지, 단위 테스트(pytest·gtest) 통과 여부, 코드 스타일을 검사한다. 실기가 필요한 테스트는 시뮬레이션(Gazebo)으로 대체하기도 한다. 핵심 효과는 **"main이 깨진 채로 하루가 시작되는 일"의 차단** — 사람은 잊어도 CI는 잊지 않는다.

**심화 — 되돌리기 도구**는 대상 공간마다 다르다.

| 상황 | 명령 | 비고 |
|---|---|---|
| 작업 디렉터리의 수정을 버린다 | `git restore 파일` | |
| add한 것을 스테이징에서 뺀다 | `git restore --staged 파일` | |
| 공유된 잘못된 커밋을 무효화 | `git revert 커밋ID` | 반대 변경을 새 커밋으로 추가 — 이력 보존 |
| 나만 가진 최근 커밋을 물린다 | `git reset --soft HEAD~1` | 로컬 이력만 |
| 커밋을 잃은 것 같다 | `git reflog` | HEAD 이동 기록에서 복구 |

원칙은 rebase와 같다 — **이 커밋을 다른 사람이 봤다면 무조건 revert**(추가로 되돌리기), 나만 가진 이력이면 reset으로 수정해도 안전하다.

   **채점: X**

2. 분산 버전관리 시스템에서 GitHub 서버가 다운되어도 팀의 작업이 계속될 수 있는 이유는 무엇인가? (중앙집중형 VCS와 대비하여 서술) - 단계가 4분할 되어있기 때문 원격 접근이 불가 해도 로컬에서는 작업이 가능하다.
   **채점: △**
   > [!question]- 정답 및 해설
   > **정답:** **분산(distributed)** 구조 — 모든 개발자 PC에 저장소 전체 이력의 완전한 복사본이 있다. 원격(GitHub)은 팀이 합의한 "만남의 장소"일 뿐이며 push·pull·clone 할 때만 네트워크가 필요하다. (SVN 같은 중앙집중형은 서버가 없으면 커밋 자체가 불가능하다.)
   > **해설:** "로컬에서 작업 가능하다"는 결론은 맞지만, 근거로 든 "4단계 분할"은 이 질문과 무관한 개념이다. 4개 공간(작업 디렉터리·스테이징·로컬 저장소·원격 저장소)은 데이터가 이동하는 절차 구분이고, 지금 질문의 핵심은 "로컬 저장소가 원격의 부분 캐시가 아니라 전체 이력의 완전한 복사본"이라는 분산 구조 자체다.

3. `git add`와 `git commit`은 각각 어떤 공간으로 데이터를 이동시키는가? 4개 공간의 순서대로 쓰시오. - add : 로컬 -> 스테이징, commit : 스테이징 -> 스냅샷
   **채점: △**
   > [!question]- 정답 및 해설
   > **정답:** 작업 디렉터리 → (`git add`) → 스테이징 영역 → (`git commit`) → 로컬 저장소(.git) → (`git push`) → 원격 저장소
   > **해설:** `add`의 출발점은 "로컬"이 아니라 **작업 디렉터리**이고, `commit`의 도착점은 "스냅샷"이 아니라 **로컬 저장소**다(스냅샷은 커밋이 만들어내는 결과물이지 공간 이름이 아니다). 또한 "4개 공간의 순서대로 쓰시오"라는 요구에 맞춰 전체 순서를 나열하지 않았다.

6. 로컬에만 있는(아직 push하지 않은) 커밋과 이미 push된 커밋 중, rebase를 써도 안전한 쪽은 어느 것이며 그 이유는? - 모르겠음
   **채점: X**
   > [!question]- 정답 및 해설
   > **정답:** **아직 push하지 않은, 나만 가진 로컬 커밋.**
   > **해설:** rebase는 커밋을 "새로 다시 쓰는" 작업이다. 이미 push되어 다른 사람이 봤을 수 있는 커밋을 rebase하면, 팀원 로컬에는 옛 커밋이 남고 원격에는 새 커밋이 생겨 이력이 갈라진다. 강제 push를 하게 되면 남의 커밋이 사라지거나 pull마다 유령 충돌이 발생한다. 반면 나만 아는 로컬 커밋은 아무도 그 위에 작업을 쌓지 않았으므로 자유롭게 재작성해도 안전하다.

7. `get_max_speed()` 함수에서 merge 충돌이 발생했다면, `<<<<<<< HEAD`와 `>>>>>>> feature/...` 사이에는 각각 어느 브랜치의 코드가 표시되는가? - 둘다
   **채점: X**
   > [!question]- 정답 및 해설
   > **정답:** `<<<<<<< HEAD` 쪽에는 **현재 체크아웃한 브랜치**(예시에서는 merge를 받는 쪽, 보통 main)의 코드가, `=======` 아래 `>>>>>>> feature/...` 쪽에는 **병합해 들어오려는 상대 브랜치**(feature/speed-tuning)의 코드가 표시된다.
   > **해설:** "둘 다"는 두 코드가 표시된다는 사실만 말할 뿐, 질문이 원한 "어느 쪽에 어느 브랜치가 오는가"라는 대응 관계를 답하지 않았다.

10. 공유된 main에 잘못된 커밋이 올라갔을 때 이력을 보존하며 되돌리는 명령과, 아직 나만 가진 로컬 커밋을 되돌릴 때 쓰는 명령을 각각 쓰시오. - restore, restore --staged
    **채점: X**
    > [!question]- 정답 및 해설
    > **정답:** 공유된 잘못된 커밋(이력 보존) → **`git revert 커밋ID`**(반대 변경을 새 커밋으로 추가). 나만 가진 로컬 커밋 → **`git reset --soft HEAD~1`**.
    > **해설:** `git restore`/`git restore --staged`는 아직 커밋되지 않은 작업 디렉터리·스테이징 영역의 변경을 되돌리는 명령이며, "커밋을 되돌리는" 이번 질문(revert/reset)과는 대상 자체가 다르다.
