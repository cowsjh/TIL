1번 문항

Git이 프로젝트의 변경 이력을 관리하는 방식에 대한 설명으로 가장 적절한 것은?

B. 각 커밋은 그 시점 프로젝트 전체 모습의 스냅샷이며, 부모를 가리키는 사슬로 연결된다

에이타니

정답이에요

Git은 변경 차이가 아니라 특정 시점의 프로젝트 전체 모습을 스냅샷으로 저장합니다. 각 스냅샷이 커밋이며 고유 해시 ID를 갖고, 부모 커밋을 가리키는 사슬로 연결되어 이력을 형성합니다. 이는 diff 기반 시스템과 Git을 구분하는 핵심 특징입니다.

에이타니

2번 문항

작업 디렉터리에서 수정한 파일 중 커밋에 포함할 변경만 골라 담는 중간 공간의 이름은 무엇인가요?

stage

에이타니

오답이에요

Git은 작업 디렉터리, 스테이징 영역, 로컬 저장소, 원격 저장소의 4개 공간으로 나뉩니다. 스테이징 영역은 git add로 커밋할 변경만 선택적으로 담는 중간 단계로, 의미 있는 단위로 커밋을 나누기 위해 존재합니다.

에이타니

3번 문항

merge와 rebase의 차이에 대한 설명으로 옳은 것은?

B. merge는 병합 커밋을 새로 만들어 이력을 보존하고, rebase는 커밋을 최신 브랜치 끝으로 재배치해 이력을 한 줄로 만든다

에이타니

정답이에요

merge는 두 갈래를 합치는 병합 커밋을 만들어 브랜치가 갈라지고 합쳐진 이력을 그대로 보존합니다. 반면 rebase는 내 커밋들을 최신 main 끝으로 옮겨 다시 쌓아 한 줄의 깔끔한 이력을 만들지만, 원래 커밋을 새 커밋으로 다시 씁니다. 이미 공유된(push된) 커밋에는 rebase를 사용하면 안 됩니다.

에이타니

4번 문항

같은 파일의 같은 부분을 양쪽 브랜치에서 다르게 수정해 Git이 자동으로 병합하지 못하고 사람의 판단을 요구하는 상황을 무엇이라고 하나요?

conflict

에이타니

정답이에요

충돌은 merge나 rebase 과정에서 같은 부분이 양쪽에서 다르게 변경되어 Git이 어느 쪽이 옳은지 판단할 수 없을 때 발생합니다. 이는 오류가 아니라 사람이 최종 결정을 내려야 한다는 정상적인 신호이며, <<<<<<<, =======, >>>>>>> 표식으로 표시됩니다. 해결 시 두 변경의 의도를 통합하는 것이 중요합니다.

Pull Request(PR)와 CI를 활용하는 협업 워크플로우의 목적으로 가장 적절하지 않은 것은?

C. 리뷰 없이도 빠르게 병합할 수 있도록 절차를 최소화한다

에이타니

정답이에요

PR과 CI는 오히려 리뷰와 자동 테스트라는 검증 절차를 거치도록 만들어 코드 품질을 지키는 것이 목적입니다. 리뷰는 결함 조기 발견, 지식 공유, 컨벤션 유지 효과가 있고, CI는 빌드·테스트·린트를 자동화해 main이 항상 동작하는 상태를 유지하게 합니다. 절차를 최소화하는 것은 이 워크플로우의 취지와 반대됩니다.
