## 2강. 로봇 소프트웨어 스택과 실시간성

### 핵심 개념

로봇 소프트웨어는 **인지(Perception) → 판단(Planning) → 제어(Control)**의 폐루프로 구성된다. 인지는 센서 원시 데이터를 상태 추정치로, 판단은 그 정보로 행동 결정을, 제어는 결정을 모터 명령으로 바꾼다. 사람이 뜨거운 주전자를 만졌을 때(피부→인지, 위험 판단→판단, 손 뗌→제어) 일어나는 반사와 같은 흐름이다.

계층마다 갱신 속도가 다른 **멀티레이트(multi-rate) 구조**이며, 빠른 루프는 느린 루프를 기다리지 않고 "가장 최신 값"만 갈아 끼운다 — ROS2의 Topic이 비동기 발행-구독 구조인 이유다.

| 계층 | 전형적 주기 | 결정 요인 |
|---|---|---|
| 제어 | 100Hz~10kHz | 모터·기구의 동역학 |
| 인지 | 10~60Hz | 센서 프레임률(카메라 30fps, LiDAR 10~20Hz) |
| 판단(지역) | 5~20Hz | 환경 변화 속도 |
| 판단(전역) | 0.1~1Hz | 목표·지도 변화 빈도 |

> 핵심 원칙: 빠른 루프는 느린 루프를 기다리지 않는다. 이를 어기면 우선순위 역전·블로킹으로 제어 주기가 무너진다.

**인지 계층**의 핵심은 여러 센서를 융합해 "가장 그럴듯한 현재 상태"를 계산하는 상태 추정(state estimation)이다. 센서별 특성 차이가 뚜렷하다.
- **encoder** — 즉각 피드백은 가능하지만, 헛바퀴(슬립)는 신호만으로 측정하기 어렵다.
- **IMU** — 자체 센서라 빠르지만 자석 영향을 크게 받아 모터 근처에 두면 안 되고, 지구 자기장을 기준으로 측정하며, 적분 특성상 오차가 계속 누적된다.
- **GPS** — 위성 신호를 기다려야 해서 느리지만, 드리프트(누적 오차)는 없다.
- 세 센서가 서로의 약점을 보완하므로(예: IMU+GPS 융합), 반드시 **캘리브레이션**이 필요하다.

**판단 계층**은 전역계획(지도 전체에서 목적지까지 경로, 느려도 됨)과 지역계획(눈앞 장애물 회피, 짧은 주기로 갱신)으로 나뉜다.

**제어 계층**은 목표-측정 오차를 매 주기 끊임없이 보정한다(PID 등). 서보 모터는 PWM으로 구동되며, DC 모터에서 BLDC로 전환되는 흐름도 이 계층과 맞닿아 있다.

**주기·지연·지터**는 서로 독립된 개념이다.
- **주기(Period)**: 작업이 얼마나 자주 반복되는가
- **지연(Latency)**: 입력이 들어와 출력이 나오기까지 걸리는 시간
- **지터(Jitter)**: 주기(또는 지연)가 얼마나 들쭉날쭉한가

PID 같은 디지털 제어기는 "일정한 Δt" 가정 위에서 적분(오차×Δt 누적)·미분(오차변화÷Δt)을 계산한다. 지터가 크면 이 가정이 깨져 계산이 매 주기 틀어지고 제어 출력에 노이즈가 실리며, 심하면 시스템이 진동·발산한다. 즉 지터는 단순 성능 저하가 아니라 **제어 이론의 전제를 깨뜨리는 문제**다.

실시간성은 "빠르다"가 아니라 "마감을 보장한다"는 뜻이며, 마감 초과 시 결과에 따라 등급이 갈린다.

| 등급 | 마감 초과 시 | 예 |
|---|---|---|
| Hard | 치명적 실패 | 모터 전류/속도 제어 루프, 비상정지(E-Stop) |
| Firm | 가치 0으로 폐기 | 카메라 프레임 기반 객체 인식 |
| Soft | 가치 점진적 하락 | 지도 갱신·경로 재계획, 로그 업로드 |

등급에 따라 실행 환경이 갈린다 — Hard는 지터를 보장하는 MCU/RTOS에, Firm/Soft는 리눅스 Edge 컴퓨터에 둔다(1강의 연산 분담과 연결).

지터의 원인은 OS 스케줄러(공평성 위주라 CPU 배분 시점 미보장), 인터럽트·다른 프로세스 간섭, 캐시 미스, 동적 메모리 할당·GC 등이며, RTOS(우선순위 기반 선점형 스케줄링), 리눅스 PREEMPT_RT 패치, 제어 루프 내 동적 할당·블로킹 금지 같은 결정론적 코드 작성으로 줄인다.

## 3강. 리눅스와 로봇 개발환경

### 핵심 개념

로봇 온보드 컴퓨터는 모니터·키보드가 없는 헤드리스 환경이라 리눅스(Ubuntu)가 표준이다 — 오픈소스라 커널 수준까지 손댈 수 있고(PREEMPT_RT 등), 가볍고, SSH·systemd 같은 원격·자동화 도구가 처음부터 갖춰져 있으며, ROS2·OpenCV·PyTorch의 1차 지원 대상이라 생태계가 크다.

리눅스는 **사용자 공간 / 커널** 두 세계로 나뉜다. 셸·ROS2 노드·파이썬 등은 사용자 공간에서 돌고, 파일·장치 접근은 반드시 시스템 콜로 커널에 요청해야 한다 — 프로그램이 하드웨어를 직접 건드릴 수 없어 하나가 죽어도 시스템 전체는 살아남는다. 실행 중인 프로그램은 **프로세스**(고유 PID, 독립 메모리, 커널 스케줄러가 CPU 배분 — 2강의 지터가 바로 여기서 생긴다)이며, `ps aux`/`htop`으로 확인하고 `kill PID`로 종료한다.

리눅스의 설계 철학은 **"모든 것은 파일(everything is a file)"** — 키보드, USB 시리얼, 카메라도 전부 open/read/write로 다룰 수 있다. `/dev/ttyUSB0`(시리얼), `/dev/video0`(카메라)처럼 하드웨어가 파일로 노출되어, 파이썬의 `open('/dev/ttyUSB0')`로 바로 통신할 수 있다.

로봇 개발에서 자주 만나는 디렉터리:

| 경로 | 용도 |
|---|---|
| `/home` | 사용자 작업 공간 |
| `/etc` | 시스템 설정(udev rules 포함) |
| `/opt` | 외부 소프트웨어(ROS2 등) |
| `/proc` | 커널이 만드는 가상 정보 |
| `/dev` | 장치 파일 (하드웨어가 파일로 나타나는 곳) |

리눅스는 다중 사용자 시스템이라 파일마다 소유자(u/그룹 g/그 외 o)별 **rwx** 권한이 있다. `ls -l` 결과가 `-rwxr-xr--`이면 소유자는 읽기·쓰기·실행, 그룹은 읽기·실행, 그 외는 읽기만 가능하다는 뜻이다. 권한은 `chmod`, 소유자는 `chown`으로 바꾼다.

가장 흔한 권한 이슈는 **시리얼 포트 접근**이다. `/dev/ttyUSB0`은 보통 `dialout` 그룹 소유라 내 계정이 그 그룹에 없으면 `Permission denied`가 난다. 정석 해결은 `sudo usermod -aG dialout $USER`로 그룹에 추가하는 것이며, 매번 `sudo`를 붙이거나 소유자를 바꾸는 건 원인을 회피하는 임시방편이다.

> 주의: `sudo`는 시스템 전체를 지울 수 있는 권한이다. "에러 나면 일단 sudo"는 금물 — `sudo colcon build`로 빌드 산출물이 root 소유가 되면 이후 일반 권한 빌드가 계속 깨지는 자충수가 된다.

**bash 필수 명령**은 범주로 정리하면 외우기 쉽다.

| 범주 | 명령 |
|---|---|
| 탐색 | `pwd` / `ls -l` / `cd` |
| 파일 | `cp` / `mv` / `rm -r` / `mkdir -p` |
| 내용 | `cat` / `less` / `tail -f` |
| 검색 | `grep -r` / `find . -name` |
| 프로세스 | `ps aux` / `htop` / `kill` / `kill -9` |
| 장치·시스템 | `lsusb` / `dmesg` / `df -h` |

`|`(파이프)로 작은 도구를 조합하는 것이 리눅스 철학의 정수다 (예: `ps aux | grep ros`).

**SSH**는 헤드리스 로봇에 접속하는 암호화 원격 터미널이다. `ssh robot@192.168.0.42`처럼 IP나 mDNS 호스트명으로 접속하며, 비대칭 암호화 기반 키 인증(`ssh-keygen` → `ssh-copy-id`)으로 비밀번호 없이 자동화할 수 있다.

**네트워크**: 원격 제어는 기본적으로 같은 네트워크 안에 있어야 하며, 방화벽(UFW), HTTPS/HTTP, SHA 기반 암호화가 관련된다. 로봇에는 보통 외부 중계기를 두어, IP가 바뀌어도 포트포워딩으로 다른 IP에서 특정 로봇을 조종할 수 있게 한다. IPv4는 `192.168.0.xxx`처럼 표기하고, IPv6는 자릿수를 늘려 더 많은 주소를 표현한다.

USB 포트 이름(`/dev/ttyUSB0`처럼 긴 이름)을 SSH로 접속해 그대로 쓰기보다 `/lidar`처럼 짧게 매핑해 두는 것이 **udev rules**다. LiDAR·모터보드처럼 USB 장치가 여러 개면 부팅 순서에 따라 `/dev/ttyUSB0`/`ttyUSB1` 번호가 뒤바뀔 수 있어, 경로를 코드에 하드코딩하면 위험하다. `idVendor`/`idProduct`(+필요시 `serial`)로 장치를 식별해 `/etc/udev/rules.d/`에 규칙을 작성하면 `/dev/lidar`처럼 고정 이름을 만들 수 있고, `sudo udevadm control --reload-rules && sudo udevadm trigger`로 즉시 적용한다. 같은 모델 장치를 여러 개 쓸 때는 포트를 고정할 수밖에 없으므로 `serial`로 구분한다.

|---|---|---|---|
| 1 | 인지-판단-제어 세 계층의 전형적인 주기를 빠른 것부터 나열하면? | **제어 > 인지 > 판단** | 제어는 100Hz~10kHz, 인지는 10~60Hz, 판단(지역)은 5~20Hz, 판단(전역)은 0.1~1Hz로 동작한다. 각 계층은 기구적 동역학·센서 프레임률·환경 변화 속도라는 서로 다른 요인으로 주기가 결정된다. |

| 3 | 다음 중 Hard 실시간 작업으로 가장 적절한 것은? | **모터 전류/속도 제어 루프** | Hard 실시간은 마감 초과 시 가치가 음수(치명적 실패)가 되는 작업이다. 모터 전류/속도 제어는 마감 초과 시 제어 불안정·하드웨어 손상으로 이어진다. 반면 객체 인식은 Firm, 경로 재계획·로그 업로드는 Soft 등급이다. |
| 4 | USB 장치가 부팅 순서에 따라 `/dev/ttyUSB0`, `/dev/ttyUSB1`처럼 번호가 뒤바뀌는 문제를, 장치 고유 식별자 기준으로 고정된 이름을 부여해 해결하는 커널 장치 관리 규칙은? | **udev rule** | idVendor·idProduct·serial 등 식별자를 가진 장치가 연결되면 지정한 이름의 심볼릭 링크를 생성하는 udev의 규칙이다. 부팅 순서가 바뀌어도 코드에서는 항상 고정된 이름(`/dev/lidar` 등)으로 장치에 접근할 수 있다. |
| 5 | 일반 계정으로 `/dev/ttyUSB0`(소유자 root, 그룹 dialout)에 접근할 때 Permission denied가 발생하면, 정석적인 해결은? | **내 계정을 dialout 그룹에 추가한다** | `usermod -aG dialout $USER`로 그룹에 추가하는 것이 정석이다. 매번 sudo를 붙이는 습관은 원인을 파악하지 않은 임시방편이며, 소유자를 바꾸거나 권한을 777로 여는 것은 보안·설계 원칙에 어긋난다. |
